## Introduction

Compute Flow provides the Compute Flow Brick Manager. It:

- Discovers bricks for building extraordinary AI pipelines at the edge.
- Installs bricks and the Compute Flow core libraries.

The Compute Flow Brick Manager builds on top of the design principles of Compute Flow core:

- Compute Flow follows a [compatibility principle](../PRODUCT.md#compatibility-principle): bricks
  built against previous brick and runner API versions must continue to work with newer releases.

It is intended to help all developers create new bricks and is designed for simplicity over strict
dependency resolution – bricks can be added, updated, and removed without worrying about dependency
graphs or version conflicts.

The Compute Flow Brick Manager is the user's first introduction to the brick ecosystem and is the
starting point to building AI applications with Compute Flow. It installs brick source trees and
their model artifacts, builds the core library, and provides a thin build command for the standard
Compute Flow CMake targets.

## Quickstart

Run these commands from the Compute Flow project root.

Set up the project environment:

```bash
# Install uv if you haven't already
curl -LsSf https://astral.sh/uv/install.sh | sh

# Sync the project's dependencies
uv sync

# Activate the project's virtual environment
source .venv/bin/activate
```

Then use `compute-flow ...` to invoke the Compute Flow Brick Manager:

```bash
# Check for the brick manager system dependencies
compute-flow check

# Update the local registry cache
compute-flow update

# Install one model and the latest brick implementation when none is installed
compute-flow model install tts:qwen3-tts qwen3-tts-0-6b-custom-voice

# Show the models declared by the installed brick version
compute-flow model list tts:qwen3-tts

# Show install details for one model
compute-flow model info tts:qwen3-tts qwen3-tts-0-6b-custom-voice

# Uninstall all model artifacts for one brick
compute-flow model uninstall tts:qwen3-tts --all

# It is possible to also install all bricks from the cache
compute-flow brick install --all

# Uninstall a specific brick and all of its model artifacts
compute-flow brick uninstall tts:qwen3-tts

# Uninstall all installed bricks and their model artifacts
compute-flow brick uninstall --all

# Build the project with installed bricks
compute-flow build native
```

Pass `--streamline` to compile Arm® Streamline timeline annotations into native Linux®,
`linux_arm64`, or `android_arm64` builds. The build command always sets this option explicitly, so
reusing a build directory does not retain stale annotation state. See
[Capturing Arm® Streamline traces on Linux® and Android™](../howto/capturing_streamline_traces.md)
for target setup and capture steps.

## Brick Identifiers

Commands select bricks with:

```text
<type>:<name>[@version]
```

`type` is the brick type. `name` is the brick variant, derived from the `name` field in the brick's
`info.json`. For example, `Qwen3TTS` in `info.json` becomes `qwen3-tts`:

```bash
tts:qwen3-tts@1.0.0
```

In command syntax, `name` is the brick manager name, not the implementation class name from
`info.json`. The manager derives this name from `info.json` `name` instead of requiring another
user-defined metadata field. This keeps brick commands lowercase and consistent across the registry,
while leaving brick authors with a single implementation name to choose.

The manager name is generated by splitting CamelCase and acronym boundaries, replacing underscores
with hyphens, and lowercasing the result. For example:

```text
Qwen3TTS -> qwen3-tts
PerchV2 -> perch-v2
```

`@version` is optional for `info` and `install`. If it is omitted, the manager selects the latest
available version from the cache. If it is provided, the manager selects that exact cached version.

Installed state has a strict single-version rule: for a given `<type>:<name>`, at most one version
MAY be installed at any time. Installing a different version of an already installed brick replaces
the installed version; the manager MUST NOT leave multiple installed versions of the same brick in
the local state.

`uninstall` takes `<type>:<name>` without `@version` because there is only one installed version to
remove for each brick.

## Bricks And Models

A brick and a model are distinct concepts.

A brick is the implementation code used for model inference. Bricks are installed into the local
brick source tree and participate in the Compute Flow build.

A model is a data asset used by a brick. Models typically contain neural network weights, manifests,
tokenizers, vocabularies, or other runtime assets. Models are not built by CMake and are stored
separately from brick sources. For example, brick source code can live in Compute Flow or another
source repository, while its model weights and assets can live in a separate repository such as
Hugging Face.

Each model declares one or more ordered sources. The manager tries each source until one downloads
and passes package checksum validation. Hugging Face Hub sources use the Hugging Face Hub SDK,
including its download progress and saved or environment-provided credentials. Git sources use Git
and Git LFS. Local sources copy an existing file or directory.

A brick may declare zero, one, or many models in its `info.json` metadata.

Users can use `compute-flow model import` to supply their own model artifacts for a brick, including
models optimized for their target device. Import is available for any brick with a declared model
whose manifest can serve as a template; it is not specific to llama.cpp. The new model must be
compatible with the brick and the template manifest's runner, inputs, outputs, and other settings.
For example, users can import a compatible ONNX model for `vad:silero-vad`, or a llama.cpp GGUF
model for `lm_text:lm-text-generic`.

Model declarations are version-scoped. Each brick version owns the model declarations in its own
`info.json`, and the same model name can refer to different artifacts in different brick versions.

For that reason, model installation always resolves one brick version before downloading its model
artifacts. If a brick version is already installed, `compute-flow model install` uses that version
without reinstalling its source. If the brick is missing, the command selects the latest cached
version and installs it.

`compute-flow model install` does not accept `@version`, so it cannot implicitly switch an installed
brick to another version. Users select a specific version explicitly with
`compute-flow brick install <type:name>@<version>` before installing its models.

Compute Flow enforces a strict single-version rule for brick source installation: only one version
of a given `<type>:<name>` can be installed at a time. Other model commands operate on that
installed version, except `compute-flow model list`, which can inspect a specific cached version.

When no brick is installed, an unversioned model command uses the latest cached version's
`info.json`:

```bash
# Uses the latest cached info.json because example-tts is not installed.
compute-flow model list tts:example-tts

# Installs that cached brick snapshot, then installs its declared model.
compute-flow model install tts:example-tts example-model
```

Installed model commands use the `info.json` snapshot recorded when the brick was installed.

For example, if version `2.0.0` becomes available after version `1.0.0` was installed:

```bash
# Uses the installed 1.0.0 metadata snapshot.
compute-flow model list tts:example-tts
```

This lists the models declared by the installed `1.0.0` brick. Models added only in version `2.0.0`
are not shown.

However, if the user specifically requests version `2.0.0`:

```bash
# Uses the 2.0.0 metadata from the registry cache.
compute-flow model list tts:example-tts@2.0.0
```

This lists the models declared by the cached `2.0.0` metadata without changing the installed brick
or its model state.

The recorded snapshot and the installed `info.json` must agree. `compute-flow update` refreshes the
registry view but does not silently change the installed brick.

## Brick Registry

The packaged `registry.txt` is the default source list. Each line identifies one unique brick
source.

```text
https://gitlab.example.com/team/brick-code.git
/Users/me/dev/bricks/local_tts_brick
../experimental-bricks/local_stt_brick
```

Use `--registry` to select a different source list:

```bash
compute-flow update --registry /path/to/registry.txt
```

`compute-flow registry add <git-url>` stores a Git URL in `$COMPUTE_FLOW_HOME/registry.txt` (or
`~/.compute-flow/registry.txt`). `registry remove` removes a source from that user registry, and
`registry list` shows both packaged and user sources. Run `compute-flow update` after adding or
removing a source to refresh the cache. By default, `update` reads both registries. Passing
`--registry <path>` to any registry command or to `update` selects only that file; add and remove
edit it, and `update` reads it.

The registry allows working with remote and local sources in the same workflow.

- Relative local paths are resolved relative to the selected `registry.txt`, not relative to the
  process working directory.
- Git URLs may use HTTPS, SSH, Git, or file transport, including Git's `git@host:path` SSH syntax.
  Versions are discovered from tags. `update` reads each tag's root `info.json` without installing
  the brick, and records the tag and commit for that version. A Git source must have at least one
  tag, and each tag must contain valid brick metadata. Two tags declaring the same brick identity
  and version are an error.
- Local sources are ordinary directories and do not need to be git repositories.

The Compute Flow Brick Manager operates around a local indexer model meaning it maintains a local
cache of available bricks and their metadata. The generated cache lives at
`$COMPUTE_FLOW_HOME/cache.json`, or `~/.compute-flow/cache.json` by default. The cache file is
automatically generated and should not be manually edited; instead, update it through
`compute-flow update`, `brick install`, and `brick uninstall`.

When `update` runs, `$COMPUTE_FLOW_HOME/cache.json` is regenerated from the current registry.
Entries removed from the registry no longer remain listed in the refreshed cache unless they are
currently installed. An installed entry and its `info.json` snapshot remain cached until the brick
is replaced or uninstalled, so model commands continue to use declarations compatible with the
installed source. This cache is used by other commands to provide fast responses without needing to
fetch remote metadata on every command.

Updating the registry cache does not update an installed brick source tree. If a local source
changes after `update`, refresh the cache before installing it:

```bash
compute-flow update

# Edit the local brick's info.json.
compute-flow brick install tts:example-tts@1.0.0
# Error: the source metadata changed after it was cached.

compute-flow update
compute-flow brick install tts:example-tts@1.0.0 --force
# Installs the newly cached source snapshot.
```

When the refreshed registry contains changed metadata for an installed version or a newer brick
version, `compute-flow update` reports the installed and available identities and recommends the
explicit forced installation command.

This is in contrast to other package managers like HomeBrew or Arduino Library Manager which
maintain an index of available packages on a remote server for the client to fetch. As Compute
Flow's brick ecosystem grows, we may introduce a remote indexer service to reduce load on users'
machines.

## Brick Metadata

Each brick source owns its metadata in a root `info.json` file. The registry points to sources;
`info.json` says what each source contains.

```json
{
  "name": "ExampleTTS",
  "type": "tts",
  "api": "tts.v1",
  "description": "Example text-to-speech brick.",
  "author": "Example Publisher",
  "version": "1.0.0",
  "deps": ["nlohmann_json"],
  "models": {
    "example-model": {
      "description": "Example model assets.",
      "sources": [
        {
          "kind": "huggingface",
          "url": "https://huggingface.co/example/example-model",
          "ref": "1.0.0"
        }
      ],
      "sha256": "<expected-sha256>"
    }
  }
}
```

Required top-level fields:

- `name`: brick implementation name, C++ class name, and root implementation file stem. The value is
  case-sensitive. The brick manager derives the user-facing name from this value; for example,
  `ExampleTTS` becomes `example-tts`.
- `type`: brick implementation group used in brick identity strings such as `tts:example-tts`. It
  also maps to the C++ namespace under `compute_flow::bricks::<type>`.
- `api`: public brick API contract implemented by the brick. The value must match a `name` field in
  one of the JSON files under `brick_apis/`, such as `tts.v1` or `object_detection.v1`.
- `description`: short user-facing description of the brick.
- `author`: brick publisher or maintainer.
- `version`: brick release unit identifier.
- `models`: object containing model declarations keyed by model name.

Optional top-level fields:

- `deps`: list of Compute Flow-managed dependency names required by the brick implementation, such
  as `libnpy` or `nlohmann_json`. These names are consumed by generated build logic and are distinct
  from model artifacts listed under `models`.

The `type` and `api` fields are intentionally separate. `type` identifies where the implementation
belongs in the brick manager namespace. `api` identifies the public input/output tensor contract
implemented by that brick. Multiple `tts` variants can implement `tts.v1`.

The `version` field describes a release unit of the brick. If the brick is hosted on GitHub, the
version should match its release tag. The brick manager may support multiple versions in the future.

The Compute Flow brick manager will not index a brick when:

- `info.json` is missing.
- `name`, `type`, or `api` is missing.
- `<name>.cpp` or `<name>.h` is missing from the brick root.
- The C++ class is not declared in `compute_flow::bricks::<type>`.
- `api` does not match a known file under `brick_apis/`.
- `deps` contains an unknown Compute Flow-managed dependency.

A brick with no model assets uses an empty object:

```json
{
  "models": {}
}
```

Bricks must contain `info.json` or they will not be indexed by the brick manager. Model entries
require `description`, a non-empty `sources` list, and `sha256`. Each source has only these fields:

- `kind`: download mechanism. Supported values are `git`, `huggingface`, and `local`.
- `url`: repository URL, or a file URL or path for a local source.
- `ref`: immutable repository revision. This is required except for `local` sources.

Sources are tried in list order. A source is accepted only when the downloaded package passes the
same `SHA256SUMS` validation described below. Authentication is read from the corresponding SDK or
Git configuration and is not stored in `info.json`.

The `sha256` field is the expected SHA256 checksum of the model repository's `SHA256SUMS` file.
`SHA256SUMS` is a text manifest that lists the expected SHA256 checksum for each file that belongs
to the model artifact. From the Compute Flow project root, model publishers MUST generate it with:

```bash
scripts/generate_checksum.py <model-bundle-root>
```

The script recursively includes every regular file in the model bundle, including optional CLI
inputs under `samples/` and files in other subdirectories. It excludes the generated root
`SHA256SUMS` and any path with a component that starts with `.`, so dotfiles and files under
dot-directories are omitted.

Then model publishers should compute the value to put in `info.json` with:

```bash
shasum -a 256 SHA256SUMS
```

The first field of this command's output is the `sha256` value for the model entry in `info.json`.

Per-file SHA256 validation MUST happen only when the manager installs a model artifact with
`compute-flow model install`. During that installation, the manager MUST first verify the downloaded
files against `SHA256SUMS` using the equivalent of:

```bash
shasum -a 256 -c SHA256SUMS
```

Then it MUST compute the SHA256 checksum of the `SHA256SUMS` file itself and compare that value with
the `sha256` in the installed brick's `info.json`. This keeps `info.json` small while allowing each
model repository to own the full per-file checksum manifest.

After a model artifact passes full per-file validation at install time, the manager records the
artifact as installed. Later brick installation workflows assume the model files remain valid unless
the installed brick version's model declaration changes. Those workflows MUST NOT perform per-file
SHA256 validation or rehash every model file just to preserve an already installed model.

## State Directory

The manager stores state under `$COMPUTE_FLOW_HOME` when it is set, otherwise under
`~/.compute-flow`.

```text
~/.compute-flow/
  cache.json
  registry.txt
  bricks/
    <type>/
      <name>/
  models/
    <type>/
      <name>/
        <model-name>/
```

Installed brick source is keyed by brick identity. Build output belongs in the user's CMake build
directory, not under `$COMPUTE_FLOW_HOME`. The installed brick's selected version, metadata
snapshot, and model install state are recorded in `cache.json`. The recorded metadata snapshot and
the installed source tree's `info.json` must agree. Only one installed source tree may exist for
each `<type>:<name>`.

`model install` verifies every file listed in `SHA256SUMS`, then compares the `SHA256SUMS` file's
SHA256 with the installed brick's declaration. Later status and brick installation checks compare
only the small `SHA256SUMS` file and recorded install state.

`model import` does not use `SHA256SUMS`. It records the model origin, template model, generated
manifest, copied manifest brick identity, and managed path in the same installed-model state used by
the normal model lifecycle. Downloads, local copies, and manifest generation are staged in a
temporary directory. The completed package replaces its destination only after every operation
succeeds.

When a brick is replaced, the manager only needs to compare an existing model artifact's
`SHA256SUMS` file hash with the `sha256` declared by the newly installed brick version. Uninstalling
a brick removes all related model artifacts instead of retaining them for a later installation.

If the `SHA256SUMS` file hash still matches the new declaration, the manager preserves the model
artifact and install state without hashing every model file again. If the hash does not match, the
manager MUST immediately delete that model artifact and remove its install state. The user can
download a compatible package with `compute-flow model install <type>:<name> <model>`.

If an installed model is no longer declared by the newly installed brick version, the manager MUST
delete that model artifact and remove its install state.

## Shell Completion

Activating the project virtual environment enables Bash and Zsh completion for `compute-flow`.
Completion reads `$COMPUTE_FLOW_HOME/cache.json` locally and never refreshes the registry or uses
the network.

Brick completion is hierarchical so a large registry does not produce one large candidate list. The
first completion lists brick types, and completion after a type lists matching brick names:

```text
compute-flow model install <TAB>
# stt:  tts:

compute-flow model install tts:<TAB>
# tts:qwen3-tts
```

After a brick is selected, model commands complete model names declared by the version that the
command will use:

```text
compute-flow model install tts:qwen3-tts <TAB>
# qwen3-tts-0-6b-base              Qwen3-TTS 0.6B Base (voice cloning) optimized for CPUs.
# qwen3-tts-0-6b-custom-voice      Qwen3-TTS 0.6B Custom Voice optimized for CPUs.
# qwen3-tts-0-6b-custom-voice-ref  Qwen3-TTS 0.6B Custom Voice reference package.
```

In Bash and Zsh, model candidates are displayed one per line with bold model names. Descriptions
begin in an aligned column while the completion still inserts only the model name.

Bash uses its standard name-only list when the current shell has a custom `WINCH` signal trap,
because that trap prevents the completion adapter from safely redrawing the prompt after the table.

Completion follows each command's selection rules. Commands that require installed state suggest
only installed bricks. `model path` suggests only active installed models. `model uninstall` also
suggests artifacts found in legacy tracked model state so users can clean them up explicitly.
`model install` and `model info` suggest models declared by the selected brick version. Commands
that accept multiple models omit names already present on the command line. Brick commands that
accept `@version` complete cached versions after the user types `@`.

For `model import`, shell completion suggests cached brick identifiers and then the template models
declared by the selected brick version. It does not complete the user-defined new model name. The
template model does not need to be installed.

The shell adapters call the hidden `compute-flow __complete` interface. This command is an internal
completion protocol, is omitted from `compute-flow --help`, and is not a user-facing command.

## Managed Tools And Toolchains

Compute Flow distinguishes system dependencies from managed tools.

System dependencies are binaries that must come from the user's environment. The Brick Manager
requires system `git` because it uses the user's Git credentials, SSH configuration, certificate
trust, and proxy setup. Native builds also require host C and C++ compilers.

Managed tools are third-party binaries that Compute Flow downloads and stores under
`$COMPUTE_FLOW_HOME/tools` when a command needs them:

- CMake `4.0.2`
- Git LFS `3.6.1`

Managed toolchains are larger target toolchains that Compute Flow downloads and stores under
`$COMPUTE_FLOW_HOME/toolchains` when a command needs them:

- Android™ NDK `r27c`
- Arm® GNU Toolchain `14.2.rel1`

Managed tools and toolchains are not installed into the user's shell environment. Compute Flow
invokes managed CMake by absolute path. For Git LFS, Compute Flow prepends the managed Git LFS
directory to the subprocess environment only when running Git LFS commands.

Users can override individual managed tools and toolchains:

| Environment variable              | Selected item                   |
| --------------------------------- | ------------------------------- |
| `COMPUTE_FLOW_CMAKE_EXECUTABLE`   | CMake executable                |
| `COMPUTE_FLOW_GIT_LFS_EXECUTABLE` | Git LFS executable              |
| `COMPUTE_FLOW_ANDROID_NDK_ROOT`   | Android™ NDK root directory     |
| `COMPUTE_FLOW_LINUX_ARM64_CC`     | Linux® Arm® 64-bit C compiler   |
| `COMPUTE_FLOW_LINUX_ARM64_CXX`    | Linux® Arm® 64-bit C++ compiler |

`COMPUTE_FLOW_LINUX_ARM64_CC` and `COMPUTE_FLOW_LINUX_ARM64_CXX` must be set together. An explicit
override takes precedence over a tool discovered on `PATH` and over the Brick Manager-managed tool.
An invalid explicit override is an error; the Brick Manager does not silently replace it with a
managed download.

`compute-flow check` reports the native compiler commands selected from `CC` and `CXX`, or `cc` and
`c++` by default, including their toolchain families, versions, and paths. It also reports the
selected tools and toolchains, their detected versions and paths, and whether each is provided by
the user or the Brick Manager. Missing managed items are reported as
`will be downloaded when needed` and do not cause `compute-flow check` to fail. The command exits
with a non-zero status when a required system dependency is missing or an explicit override is
invalid.

## Building With Installed Bricks

The normal build flow is:

```bash
uv sync
source .venv/bin/activate
compute-flow update
compute-flow brick install <brick>
compute-flow build native
```

CMake reads installed brick entries from `cache.json`. It first checks
`$COMPUTE_FLOW_HOME/cache.json` when `COMPUTE_FLOW_HOME` is set. If `COMPUTE_FLOW_HOME` is unset or
empty, it falls back to `~/.compute-flow/cache.json`.

For each installed cache entry, CMake uses the installed source path recorded by the brick manager
and adds that brick source directory to the main build. Installed brick build output is placed under
the selected CMake build directory.

The build command is a small wrapper around CMake. It uses `COMPUTE_FLOW_CMAKE_EXECUTABLE` when set.
Otherwise, it uses the pinned CMake version managed under `$COMPUTE_FLOW_HOME/tools` and downloads
that version before configuring the build when needed.

The build uses pre-built libraries when available to reduce compilation time. If they are
unavailable, it builds the enabled runtime dependencies from their pinned upstream sources. Use
`--from-source` to build them from source explicitly.

```bash
compute-flow build native
compute-flow build android_arm64
compute-flow build linux_arm64
```

- `native` uses the host compiler and writes to `build_native`.
- `android_arm64` writes to `build_android_arm64` and uses the Android™ NDK root selected by
  `COMPUTE_FLOW_ANDROID_NDK_ROOT`. When the variable is unset, the command downloads and reuses the
  recommended Android™ NDK version under `$COMPUTE_FLOW_HOME/toolchains`.
- `linux_arm64` writes to `build_linux_arm64`. On Linux® Arm® 64-bit hosts it builds natively. On
  other hosts it first uses the compilers selected by `COMPUTE_FLOW_LINUX_ARM64_CC` and
  `COMPUTE_FLOW_LINUX_ARM64_CXX`, then `aarch64-linux-gnu-gcc`/`aarch64-linux-gnu-g++` from `PATH`
  if available. Otherwise, it downloads and reuses the Arm® GNU toolchain under
  `$COMPUTE_FLOW_HOME/toolchains`.

After the CMake build succeeds, the command runs the `compute_flow_application_sdk` CMake target.
That target copies the public headers and library artifacts already present in the selected build
directory into an application SDK:

```text
build_<target>/
  sdk/
    CMakeLists.txt
    README.md
    include/
      compute_flow/
    lib/
      <libraries produced by the CMake build>
    share/
      compute_flow/
        bricks/
          <type>/
            <name>/
              info.json
```

The SDK contains the installed `info.json` snapshot for each brick included in the build. An
application can use a declared model's ordered `sources` to download it at runtime, validate its
files against the downloaded `SHA256SUMS`, then compare that file's SHA256 with the model's declared
`sha256`. The application therefore does not need to maintain a separate registry of model URLs and
checksums for the installed bricks. Rebuilding replaces the SDK directory, including all packaged
brick metadata, so removed bricks do not leave stale metadata behind.

The packaging step does not create, merge, or change libraries. The SDK contents reflect the
installed bricks and build options used to configure CMake. The included CMake script exposes the
copied files through the `compute_flow::sdk` convenience target:

```cmake
add_subdirectory("/path/to/build_<target>/sdk" compute_flow_sdk)
target_link_libraries(my_application PRIVATE compute_flow::sdk)
```

The `compute_flow::sdk` target propagates the requirement to compile the application with C++17 or
later and supplies the platform-specific link requirements of the packaged libraries.

When the SDK directory is configured as the top-level project, its CMake script also builds
`main.cpp` as an application and links it to `compute_flow::sdk`. The application executable name
comes from the editable `PROJ_NAME` variable, which defaults to `minimal_example`. This application
target is not created when another project consumes the SDK with `add_subdirectory()`.

Brick-type libraries are a general application design requirement for every brick type, including
TTS, STT, VAD, and object detection. The CMake build combines installed implementations into one
`<type>_core` archive for each installed brick type. SDK packaging copies these generic archives and
excludes concrete variant archives; it does not create or combine libraries itself.

If `compute-flow brick install` or `compute-flow brick uninstall` changes the tracked `cache.json`,
the next `compute-flow build <target>` automatically reruns configure and regenerates the
installed-brick factory for that build tree.

Rerun `compute-flow build <target>` after changing `COMPUTE_FLOW_HOME`. Also rerun configure
manually if the Compute Flow home directory itself did not exist when the build tree was first
configured.

## Building With Installed Bricks: Expert Mode

The `compute-flow build <target>` command is the recommended build entry point. Users who need
direct CMake control can still configure and build manually.

Native build:

```bash
cmake -S . -B build
cmake --build build -j4
```

Android™ Arm® 64-bit build:

```bash
export COMPUTE_FLOW_ANDROID_NDK_ROOT=/path/to/android-ndk-r27c

cmake -S . -B build_android_arm64 \
  -DCMAKE_TOOLCHAIN_FILE="$COMPUTE_FLOW_ANDROID_NDK_ROOT/build/cmake/android.toolchain.cmake" \
  -DANDROID_ABI=arm64-v8a \
  -DANDROID_PLATFORM=android-28 \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_INSTALL_PREFIX=android_arm64

cmake --build build_android_arm64 --parallel 8
```

Manual CMake builds read the same installed-brick cache as `compute-flow build <target>`.

To prepare the application SDK after a manual build, run:

```bash
cmake --build build --target compute_flow_application_sdk
```

## Autogenerated CMake for bricks

Installable bricks use CMake generated by the Compute Flow Brick Manager. The generated CMake
exposes a core target named `${name}::core`, where `name` is the brick `info.json` name. The core
target exposes the brick's root source directory as a public include directory and sets the
`COMPUTE_FLOW_BRICK_CLASS` target property to the concrete C++ class used by the generated factory.
When Python bindings are enabled, the generated CMake also builds a generated pybind11 extension
module named after the brick `info.json` name.

The generated CMake is written into the installed source copy under `$COMPUTE_FLOW_HOME`; registry
bricks must not keep handwritten `CMakeLists.txt` or root `*_pybind.cpp` files in their source
directories. The Brick Manager rejects a managed brick root when it contains root handwritten CMake
or handwritten Python binding sources.

Each brick must provide a root public header named `${name}.h`. The brick manifest's `brick.name`
must match the brick `info.json` name exactly. A mismatch is invalid and must fail validation/load,
so generated factory dispatch and Python binding dispatch always use the installed brick identity.

Generic type runners are owned by Compute Flow core. Brick source directories should contain
concrete brick implementation, metadata, manifests, and any brick-specific bindings, but they should
not own generic runner executable targets.

## Brick Manager commands

### `compute-flow check`

Checks whether required system dependencies are available on `PATH` and prints install actions for
missing dependencies. The report identifies the host C and C++ compiler commands used for native
builds, including each compiler's toolchain family, version, and path.

The command checks system `git` and the native C and C++ compilers. `CC` and `CXX` select compiler
commands when set; otherwise, the check uses `cc` and `c++`. It resolves the managed-tool overrides
listed in [Managed Tools And Toolchains](#managed-tools-and-toolchains), invokes selected
executables to detect their versions, and reports their provider and path. The check does not
download missing managed items.

If any required dependency is missing or an explicit override is invalid, the command exits with a
non-zero status.

### `compute-flow update`

Refreshes the local cache from the packaged and user registries, or only the file passed with
`--registry`.

Installed brick entries and their recorded `info.json` snapshots are retained even when the
refreshed registry no longer contains that version. Unversioned model commands therefore continue to
list and resolve models declared by the installed brick rather than models from the refreshed
registry metadata.

When an installed version's registry metadata changes, or the registry contains a newer version of
an installed brick, the command reports an available update and recommends replacing the brick
explicitly:

```bash
compute-flow brick install tts:example-tts@2.0.0 --force
```

The update command does not replace brick sources or reconcile model artifacts itself.

For Git sources, `update` temporarily clones the repository to inspect its tags. It does not copy
brick code into the managed install directory. If any source fails, the existing cache remains
unchanged.

> Run this command after adding or removing a registry source and before commands that read the
> local cache.

### `compute-flow registry add <git-url> [--registry <path>]`

Adds a Git URL to the user registry. Pass `--registry` to add it to a selected source-list file
instead. The command accepts the same Git URL forms as `registry.txt`, including HTTPS, SSH, and
`git@host:path` syntax. Adding the same URL again succeeds without changing the registry. This
command does not access the source, validate its tags, or change the cache.

Run `compute-flow update` to discover tagged versions and validate their metadata. If
`--registry <path>` was used for `registry add`, pass the same option to `update`:

```bash
compute-flow registry add https://example.com/team/example-tts.git
compute-flow update
```

The command does not install brick source code or models. After updating, use
`compute-flow brick list` to see the discovered versions, then
`compute-flow brick install <type:name[@version]>` to select one. See
[How to add a 3rd party brick](../howto/adding_3p_bricks.md) for an example.

### `compute-flow registry remove <source> [--registry <path>]`

Removes an exact source entry from the user registry. Pass `--registry` to remove an entry from that
selected file instead. Without the flag, packaged sources cannot be removed. A missing source is an
error. Run `compute-flow update` afterward (with the same `--registry` option, if used) so the cache
reflects the change.

Removing a source does not uninstall a brick or its models. Installed brick entries and their
metadata snapshots remain cached, as with `compute-flow update` when a source disappears.

### `compute-flow registry list [--registry <path>]`

Lists the configured source entries and labels their origin as packaged or user. Pass `--registry`
to list only the selected file. This command reads the source lists directly and does not refresh
the cache or access the network. Use `compute-flow brick list` to see the brick versions discovered
from those sources.

### `compute-flow brick list [--installed] [--type=<type>[,<type>...]]`

Displays available brick versions from the local cache, along with the installed version marker and
description. Pass `--type` with one or more comma-separated brick types to display only variants of
those types. Pass `--installed` to display only installed brick variants. The filters can be
combined. If both options are omitted, the command displays all cached bricks.

For example, list only text-to-speech variants:

```bash
compute-flow brick list --type=tts
```

Multiple types can be combined:

```bash
compute-flow brick list --type=tts,stt
```

List only installed text-to-speech variants:

```bash
compute-flow brick list --installed --type=tts
```

Example:

```text
Brick          Version  Installed  Description
tts:qwen3-tts  1.0.0    ✓ 1.0.0    High-quality multilingual text-to-speech using Qwen3 LLM backbone with neural codec decoder.
```

Reads `$COMPUTE_FLOW_HOME/cache.json`.

### `compute-flow model list <type:name[@version]>...`

Displays the cached models and the installed imported models from a given brick variant.

Model declarations live inside each brick version's `info.json`, so `compute-flow model list` keeps
model display separate from `compute-flow brick list`. This avoids noisy and ambiguous list output
when the same brick has multiple versions and each version can declare a different model set.

If `@version` is omitted, the manager selects the installed version and reads the installed brick's
`info.json` when one exists. If no version is installed, it selects the latest cached version. An
explicit `@version` always reads that version's cached registry metadata. When multiple brick
selectors are provided, the manager prints one model table with the resolved brick and version in
the leftmost columns.

Imported models are displayed only for the installed brick selected without `@version`, because they
are installed state rather than declarations owned by a cached version. The `Origin` column
distinguishes `Declared` and `Imported` entries. Imported models are installed by definition.

For declared models, the `Installed` column shows `✓ <version>` only when the model artifact has
recorded install state for the resolved brick version and its `SHA256SUMS` file's SHA256 matches the
`sha256` declared by the metadata being displayed. For imported models, it shows installed when the
managed package and recorded generated manifest exist.

Example:

```text
Models

Brick          Version  Model                       Origin    Installed  Description
tts:qwen3-tts  1.0.0    qwen3-tts-0-6b-custom-voice      Declared  ✓ 1.0.0    Qwen3-TTS 0.6B Custom Voice optimized for CPUs.
tts:qwen3-tts  1.0.0    qwen3-tts-0-6b-custom-voice-ref  Declared  -          Qwen3-TTS 0.6B Custom Voice reference package.
tts:qwen3-tts  1.0.0    qwen3-tts-0-6b-base              Declared  -          Qwen3-TTS 0.6B Base (voice cloning) optimized for CPUs.

vad:silero     1.0.0    silero-fp32                 Declared  -          Voice activity detection
```

Reads `$COMPUTE_FLOW_HOME/cache.json`.

### `compute-flow model info <type:name> <model>...`

Displays install details for one or more models declared by the currently installed version of one
brick, or imported for that brick.

The brick selector MUST NOT include `@version`. Model info uses the same installed-version
resolution rule as model path and uninstall: the single installed brick version determines which
model names are valid and which `info.json` declarations are authoritative. The displayed `Version`
is that installed brick version.

If the brick is not installed, the command fails and tells the user to install the brick first.

The `Status` field shows `Installed` only when the model artifact has recorded install state for the
resolved brick version and its `SHA256SUMS` file's SHA256 matches the `sha256` declared by the
installed brick's `info.json`.

If a requested model is declared by the installed brick version but its artifact is missing, stale,
or fails checksum validation, the command displays `Status: Not installed` for that model.

For an imported model, the output displays `Origin: Imported` and the template model name. Imported
status requires its managed directory and recorded generated manifest to exist; declared checksum
validation does not apply.

When a model is installed, the command displays the total size of all files in the installed model
artifact directory, the installed model location, and the manifests available in the installed model
root. For now, manifests are files matching `*manifest*.json` directly under the installed model
root directory.

Example:

```text
Model: qwen3-tts-0-6b-custom-voice
Version: 1.0.0
Status: Installed
Size: 2.4 GiB (2,630,017,584 bytes)

Location:
  /home/user/.compute-flow/models/tts/qwen3-tts/qwen3-tts-0-6b-custom-voice

Manifests:
  - qwen3_tts_custom_voice_en_manifest.json
  - qwen3_tts_custom_voice_es_manifest.json
  - qwen3_tts_custom_voice_fr_manifest.json
  - qwen3_tts_custom_voice_it_manifest.json
  - qwen3_tts_custom_voice_jp_manifest.json
  - qwen3_tts_custom_voice_ko_manifest.json
  - qwen3_tts_custom_voice_zh_manifest.json
```

Reads `$COMPUTE_FLOW_HOME/cache.json` and installed model artifact directories under
`$COMPUTE_FLOW_HOME/models/<type>/<name>/<model-name>/`.

### `compute-flow model path <type:name> <model>`

Prints the installed model artifact path for one model declared by the currently installed version
of one brick, or imported for that brick.

The command prints only the path, with no table or labels, so it can be used from shell scripts:

```bash
PACKAGE_DIR="$(compute-flow model path tts:qwen3-tts qwen3-tts-0-6b-custom-voice)"
```

If the model is declared but not installed, stale, or fails checksum validation, the command prints
an empty string and exits successfully.

The brick selector MUST NOT include `@version`. If the brick is not installed, or if the model is
not declared by the installed brick version, the command fails with a non-zero status.

### `compute-flow model install <type:name> <model>...`

Installs one or more model artifacts and ensures their required brick version is installed.

The brick selector MUST NOT include `@version`. Before changing installed state, the manager
resolves the installed brick version, or the latest cached version when the brick is missing, and
validates every requested model name against that version's `info.json`. It then installs or reuses
the brick source before installing the model artifacts.

To select a specific brick version, install it explicitly before installing its models:

```bash
compute-flow brick install tts:qwen3-tts@1.0.0
compute-flow model install tts:qwen3-tts qwen3-tts-0-6b-custom-voice
```

Example:

```bash
compute-flow model install tts:qwen3-tts qwen3-tts-0-6b-custom-voice qwen3-tts-0-6b-custom-voice-ref
```

Use `--force` to replace existing installed model artifacts even when they already match the
declared checksums:

```bash
compute-flow model install tts:qwen3-tts qwen3-tts-0-6b-custom-voice --force
```

`--force` applies only to the requested model artifacts; it does not force replacement of an already
installed brick source tree.

Resolution rules:

- If `tts:qwen3-tts` is already installed, the manager resolves models through that installed
  version. Otherwise, it selects and installs the latest cached version.
- Each requested model name MUST exist in the selected brick version's `info.json`. If any model is
  unknown, the command fails before installing the brick or downloading artifacts.
- If the selected brick version is missing, the manager installs it. If it is already installed, the
  manager reuses it.
- The manager downloads each requested artifact using the `url` and `ref` declared by the installed
  brick version.
- For Hugging Face Hub URLs, the manager uses the Hugging Face Hub SDK, including its standard token
  lookup and download progress bars. Private repositories require `HF_TOKEN` or a saved login from
  `hf auth login`.
- After download, the manager verifies the model files with `shasum -a 256 -c SHA256SUMS`. This is
  the only workflow that performs per-file SHA256 validation.
- The manager then computes SHA256 for the downloaded `SHA256SUMS` file and compares it with the
  `sha256` declared by the installed brick version.
- If either check fails, the command returns an error, does not mark the downloaded model as
  installed, and preserves any previously installed artifact.
- If all requested models pass both checksum checks, the manager records them as installed for the
  installed brick version and prints the updated model list for that brick.
- Model downloads and validation use a temporary directory. The manager replaces an existing model
  artifact only after its replacement passes integrity validation.
- If `--force` is provided, the manager downloads and validates each requested model again instead
  of reusing an artifact that already matches the declared checksums.

Reads `$COMPUTE_FLOW_HOME/cache.json`, the selected brick source, and that version's model
declarations.

Writes the brick source under `$COMPUTE_FLOW_HOME/bricks/<type>/<name>/`, writes model artifacts
under `$COMPUTE_FLOW_HOME/models/<type>/<name>/<model-name>/`, and updates install state in
`$COMPUTE_FLOW_HOME/cache.json`.

### `compute-flow model import <type:name> <template-model> <new-model-name>`

Creates a managed model package from user-provided model files and the manifest of a model declared
by the selected brick. Use it to run a compatible model that the brick does not declare, such as a
model optimized for a particular device. The command works with any runner used by the brick; it
does not convert model formats or adapt the brick to a different model interface.

The arguments are:

- `<type:name>`: the brick that will use the imported model.
- `<template-model>`: a model declared by that brick. Its manifest defines the runners, inputs,
  outputs, and package structure for the imported model.
- `<new-model-name>`: the name used to manage the imported model.

The brick and template model do not need to be installed. If the brick is installed, the command
uses that version. Otherwise, it selects the latest cached version and installs the brick after the
interactive session is confirmed, following the same version-selection rule as `model install`. The
template must be declared by the selected brick version's `info.json`.

When the template is installed, the manager reads its managed package. Otherwise, the manager
inspects root JSON files through the template's declared sources. If the package contains multiple
compatible manifests, the manager uses the first filename in alphabetical order. This initial
inspection fetches only root JSON documents, not model artifacts. A compatible manifest has the
selected brick's `type` and implementation `name` in its `brick` object.

For example:

```bash
compute-flow model import \
  lm_text:lm-text-generic \
  hy-mt2-1-8b-2bit-translation \
  llama3-2b
```

The command prompts once for every `models` entry containing `filename`. Each artifact prompt shows
the runner copied from the template manifest and the current filename, helping the user choose a
compatible replacement. Each response must be a local file path or an HTTP/HTTPS URL. It then
prompts for every manifest `configs` value; pressing Enter keeps the current value. Boolean,
integer, floating-point, and string values use their declared manifest types for parsing.

String configs accept plain text or a quoted JSON string without additional command-line options.
Unquoted input is stored literally. Input beginning with a double quote is decoded as a JSON string:
`"<think>\n\n</think>\n\n"` stores actual newlines, and `"C:\\models\\new"` stores literal
backslashes. Use JSON escaping for embedded quotes, for example `"Say \"hello\""`. Enter `""` to set
an empty string, or press Enter to keep the current value. Malformed quoted input prompts for
another value. String defaults are displayed as JSON strings so they can be copied back into the
prompt. Artifact paths and non-string configs keep their existing input format.

After displaying a summary and receiving confirmation, the manager:

1. Copies every field from the selected template manifest, applies the config changes and model
   filenames entered by the user, and writes the result as `<new-model-name>_manifest.json`.
2. Fetches the declared template package into temporary storage when it is not installed, then
   copies its non-model assets into the new package.
3. Copies local model files or downloads URL sources, replacing only the corresponding manifest
   `filename` values with installed basenames.
4. Moves the completed package to `$COMPUTE_FLOW_HOME/models/<type>/<name>/<new-model-name>/` and
   records imported provenance.

The workflow does not generate or validate `SHA256SUMS`. It does not modify the brick's `info.json`
or edit structural manifest fields such as brick identity, model keys, runners, inputs, outputs, or
runner parameters. Check that a replacement model matches those fields and any brick-specific
preprocessing and postprocessing expectations before using it; import does not validate model
compatibility.

Imported models are not added to the brick's `info.json` and are not declarations owned by a
particular brick release.

The application SDK contains only the installed brick's unmodified `info.json`, so imported models
are not included in its metadata and cannot use the declared-model runtime download workflow. To
deploy an imported model, use `compute-flow model path` to locate its completed managed package and
copy that package into the application. To make the model runtime-downloadable instead, publish the
complete package with `SHA256SUMS` and add it to a brick release's `info.json` as a declared model.

The new name uses the normal model-name validation. Existing managed state or an existing artifact
directory is an error. Pass `--force` to repeat the full interactive session and atomically replace
an existing model only after the new package succeeds:

```bash
compute-flow model import \
  lm_text:lm-text-generic \
  hy-mt2-1-8b-2bit-translation \
  llama3-2b \
  --force
```

The initial interface is interactive. When standard input is not a terminal, the command fails
before prompting or downloading and explains that non-interactive artifact and config options are
not available yet.

### `compute-flow model uninstall <type:name> <model>...`

Uninstalls one or more model artifacts for the currently installed version of one brick.

The brick selector MUST NOT include `@version`. Model uninstall uses the same installed-version
resolution rule as model info and path: the single installed brick version determines which model
names are valid.

Example:

```bash
compute-flow model uninstall tts:qwen3-tts qwen3-tts-0-6b-custom-voice qwen3-tts-0-6b-custom-voice-ref
```

Resolution rules:

- The manager resolves `tts:qwen3-tts` to the single installed brick version recorded in
  `$COMPUTE_FLOW_HOME/cache.json`.
- If `tts:qwen3-tts` is not installed, the command fails and tells the user to install the brick
  first.
- Each requested model name MUST exist in the installed brick version's `info.json`, be recorded as
  imported for that brick, or remain in legacy tracked model state. This permits explicit cleanup of
  imported and orphaned artifacts without weakening current brick installation cleanup.
- For each requested model, the manager deletes
  `$COMPUTE_FLOW_HOME/models/<type>/<name>/<model-name>/` when it exists and removes that model's
  install state from `$COMPUTE_FLOW_HOME/cache.json`.
- If the model artifact is already missing, the manager still clears any stale install state.
- After uninstalling the requested models, the manager prints the updated model list for that brick.

Use `--all` instead of model names to remove every installed or orphaned model artifact found for
the brick. Unlike explicit model uninstall, `--all` does not require the brick source to still be
installed.

Example:

```bash
compute-flow model uninstall tts:qwen3-tts --all
```

Reads and writes `$COMPUTE_FLOW_HOME/cache.json`.

Deletes model artifacts under `$COMPUTE_FLOW_HOME/models/<type>/<name>/<model-name>/`.

### `compute-flow brick info <type:name[@version]>`

Displays the full cached metadata for one brick identity.

Reads `$COMPUTE_FLOW_HOME/cache.json`.

### `compute-flow brick path <type:name>`

Prints the installed brick implementation source path.

The command prints only the path, with no table or labels, so it can be used from shell scripts:

```bash
BRICK_DIR="$(compute-flow brick path tts:qwen3-tts)"
```

If the brick is known but not installed, or its installed source directory is missing, the command
prints an empty string and exits successfully. The selector MUST NOT include `@version`; installed
state permits only one version for each `<type>:<name>`. An unknown brick fails with a non-zero
status.

### `compute-flow brick install <type:name[@version]>`

Installs the implementation source tree for one selected brick version into the local
`$COMPUTE_FLOW_HOME` directory. It does not build the brick and does not install missing model
artifacts.

Reads `$COMPUTE_FLOW_HOME/cache.json` and the selected local or remote source.

Writes:

- Brick sources under `bricks/<type>/<name>/`
- A `test/run_tests.sh` script in the installed brick when it provides `test/test_cases.yaml`
- Install state in `$COMPUTE_FLOW_HOME/cache.json`.

If `@version` is omitted, installs the latest available version from the cache. If `@version` is
provided, installs that exact cached version.

Does not install more than one selected brick. Does not leave more than one installed version of the
same brick; installing a different version of an already installed brick updates the single
installed source tree and records the newly selected version in `cache.json`.

After installing the brick source tree, the manager reconciles model artifacts already installed for
that brick against the newly installed brick version's `info.json`.

If an already installed declared model is not declared by the newly installed brick version, the
manager deletes that model artifact and removes its install state. An imported model is not removed
merely because it is absent from the new `info.json`.

For each remaining installed model declared by the newly installed brick version, the manager
computes SHA256 only for the installed model's `SHA256SUMS` file and compares that value with the
`sha256` in the newly installed version's `info.json`. If the `SHA256SUMS` file hash matches, the
manager preserves the model artifact and install state without rehashing every model file.

If the `SHA256SUMS` file is missing or its hash does not match, the manager deletes the incompatible
artifact and clears its install state.

The command output MUST tell the user which installed models were removed because they are no longer
declared by the new brick version, and which installed models were removed because their
`SHA256SUMS` file hash no longer matches the new brick version's declaration.

Models declared by the brick version but not already installed are not downloaded by
`compute-flow brick install`. After reconciling already installed models, the manager prints the
same view as:

```bash
compute-flow model list <type>:<name>@<installed-version>
```

This makes the available models visible and lets the user choose which missing artifacts to install
with `compute-flow model install <type>:<name> <model>...`.

When `test/test_cases.yaml` is present in the brick source, installation generates
`test/run_tests.sh` inside the installed source copy and displays its path. Run it with `bash`. The
YAML selects models declared in `info.json`, manifests in those models, and one or more CLI argument
lists per manifest. For each selected model, the script installs it, checks its selected manifests,
runs every test case through the brick type's Python CLI example, and uninstalls it before moving to
the next model. A failed command makes the script exit nonzero after attempting to uninstall the
active model. Native nightly CI jobs run generated scripts for installed bricks with test cases.
This first version does not validate output values. Installing an already installed brick
regenerates the script from the installed test cases. Bricks without `test/test_cases.yaml` have no
generated script.

Use `--force` to replace an existing installed source tree after confirmation. The confirmation
states that incompatible related model artifacts will also be removed. A forced install preserves
only models declared by the selected brick version whose installed `SHA256SUMS` hash matches the
corresponding `sha256` declaration.

If the brick source is a local directory then the local install is copied, not symlinked. The
copy-based workflow avoids surprising live links between development directories and installed
state. To refresh an installed local brick after editing the original source, run with `--force`.

For a Git source, the manager checks out the cached tag into temporary storage and verifies that it
still points to the commit recorded by `update`. A moved tag is an error; rerun
`compute-flow update` before retrying. The checked-out code is copied into the same managed brick
source tree used for local sources, without the Git metadata directory.

### `compute-flow brick uninstall <type:name>`

Removes the installed brick source tree and every related model artifact for one brick identity,
then updates install state.

Reads `$COMPUTE_FLOW_HOME/cache.json`.

Writes brick and model install state in `$COMPUTE_FLOW_HOME/cache.json` and deletes model artifacts
under `$COMPUTE_FLOW_HOME/models/<type>/<name>/`. It does not remove build output.

Before deleting anything, the interactive confirmation names both the brick source and related model
artifacts. Declining leaves both unchanged.

Use `--all` to remove every installed brick source tree recorded in the cache and all model
artifacts related to those bricks.

Use `--yes` or `-y` to skip the interactive confirmation prompt.

### `compute-flow build list`

Lists the supported build targets and their descriptions. The `native` description reflects the
host. For example, it can report:

```text
native -> Build natively for macOS® arm64
android_arm64 -> Cross-compile for Android™ with Arm® 64-bit CPU
linux_arm64 -> Cross-compile for Linux® with Arm® 64-bit CPU
```

On a Linux® Arm® 64-bit host such as a Raspberry Pi® 5, it reports:


### `compute-flow build <target>`

Configures and builds Compute Flow and installed bricks for one target, then copies the public
headers and built libraries into `<build-directory>/sdk`. After a successful build, the command
reports both directories.

Supported targets:

- `native`
- `android_arm64`
- `linux_arm64`

The command defaults to four parallel build jobs. Use `--jobs` or `-j` to override it:

```bash
compute-flow build native --jobs 8
```

The command uses pre-built libraries when available to reduce compilation time. It builds Protobuf,
LiteRT, ExecuTorch, ONNX Runtime, MNN, and SentencePiece from source when pre-built libraries are
unavailable. Use `--from-source` to build them from source explicitly:

```bash
compute-flow build native --from-source
```

Source builds download several GiB of upstream source and can take substantially longer than builds
using pre-built libraries. The `--jobs` value also limits nested dependency builds.

## Future Work

- `compute-flow model info` currently discovers only files matching `*manifest*.json` directly under
  the installed model root directory. Required manifests may move into subdirectories, and the role
  of each manifest is not explicit. Future model metadata should declare manifest files and their
  purposes explicitly, either in the brick `info.json` model declaration or in model-owned
  repository metadata.
