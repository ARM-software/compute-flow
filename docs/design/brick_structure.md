## Overview

A brick is a reusable inference building block. Each brick provides a C++ implementation and
optional internal implementation files. The folder layout is intentionally fixed so Compute Flow can
validate bricks and generate repetitive build and binding glue.

This document defines the required structure of a brick folder.

## Folder Layout

Each brick must follow this layout:

```text
bricks/<type>/<name>/
  info.json
  <implementation-name>.cpp
  <implementation-name>.h
  internal/
    *.cpp
    *.h
```

In this layout, the directory `<name>` is the brick manager name used in commands. The
`<implementation-name>` file stem is the value of `name` in `info.json`.

`internal/` is optional. If present, Compute Flow recursively discovers all `.cpp` files under
`internal/` as implementation sources. Header files under `internal/` are private to the brick
implementation and are not public brick headers.

The root `<implementation-name>.cpp` and `<implementation-name>.h` files are required. They are the
public implementation entry points for the brick.

CMake files and language binding source files are not expected to be present in the brick folder.
The Compute Flow brick manager generates build files and bindings from `info.json` and the fixed
folder structure.

## `name`

The `name` field in `info.json` is the brick implementation name.

It is used as:

- The C++ class name.
- The file stem for the root implementation files `<name>.cpp` and `<name>.h`.

The value is case-sensitive.

For example:

```json
{
  "name": "Qwen3TTS",
  "type": "tts",
  "api": "tts.v1"
}
```

This requires a brick source root containing:

```text
bricks/tts/qwen3-tts/
  info.json
  Qwen3TTS.cpp
  Qwen3TTS.h
```

and the implementation class:

```cpp
compute_flow::bricks::tts::Qwen3TTS
```

The brick manager name is derived from `name`, but it is not the same value:

```text
tts:qwen3-tts
```

## Brick Manager Name

The brick manager derives a lowercase name from `info.json` `name` and uses that generated name in
user-facing brick identities, installed source paths, and installed model paths. This avoids adding
another user-defined field to `info.json` and keeps brick manager commands consistent across the
registry.

The manager name is generated by splitting CamelCase and acronym boundaries, replacing underscores
with hyphens, and lowercasing the result.

Examples:

```text
Qwen3TTS -> qwen3-tts
PerchV2 -> perch-v2
LMTextGeneric -> lm-text-generic
SileroVAD -> silero-vad
```

For example, a brick whose `info.json` contains:

```json
{
  "name": "Qwen3TTS",
  "type": "tts",
  "api": "tts.v1"
}
```

is selected in the brick manager as:

```text
tts:qwen3-tts
```

The implementation remains:

```cpp
compute_flow::bricks::tts::Qwen3TTS
```

## `type`

The `type` field identifies the implementation group and maps to the C++ namespace under
`compute_flow::bricks`.

For example:

```json
{
  "type": "tts"
}
```

maps to:

```cpp
compute_flow::bricks::tts
```

and contributes the first component of the brick identity:

```text
tts:<name>
```

## `api`

The `api` field identifies the public input/output tensor contract implemented by the brick. The
value must match the `name` field of a JSON file under `brick_apis/`.

For example:

```json
{
  "api": "tts.v1"
}
```

means the brick implements the contract defined by:

```text
brick_apis/tts.v1.json
```

The `type` and `api` fields are intentionally separate. `type` identifies the implementation group.
`api` identifies the public tensor contract. Different implementation groups may implement the same
API.

## `deps`

The optional `deps` field lists Compute Flow-managed dependencies required by the brick
implementation.

For example:

```json
{
  "deps": ["libnpy", "nlohmann_json"]
}
```

These names are consumed by generated build logic. They are not model artifacts and must not be
listed under `models`.

`deps` must not contain arbitrary CMake target names. If a dependency is not managed by Compute
Flow, it must be promoted to a Compute Flow-managed dependency before generated build logic can use
it. The current supported dependency names are documented in the Compute Flow Brick Manager design.

## Brick Build And Binding Autogeneration

Compute Flow generates repetitive build and binding glue from the fixed brick structure and
`info.json` metadata. A brick author implements the C++ class; Compute Flow generates the mechanical
CMake targets, Python bindings, and future language bindings.

The generated CMake template is owned by the Compute Flow brick manager and is rendered from:

- `info.json` `name`, `type`, and `deps`.
- The required root `<name>.cpp` and `<name>.h` implementation files.
- Optional recursive `internal/*.cpp` implementation files.
- A generated pybind11 source file for the Python extension module.

For managed brick installs, generated CMake is written into the installed source copy under
`$COMPUTE_FLOW_HOME` and is the active build input. The source-tree brick directory is not modified.
Managed brick roots must not contain handwritten `CMakeLists.txt` or root `*_pybind.cpp` files. The
brick manager rejects registry bricks that still provide root handwritten CMake or handwritten
Python binding sources.

Autogeneration goals:

- Remove handwritten CMake boilerplate from brick implementations.
- Remove handwritten Python pybind boilerplate from brick implementations.
- Make future bindings, such as JNI, available without requiring each brick author to write binding
  code manually.
- Keep brick-specific implementation code handwritten and explicit.

Autogeneration does not generate the brick implementation itself and does not hide model-specific
logic, preprocessing, postprocessing, or runtime behavior.
